# MQTT contract and command lifecycle review

Status: **accepted Phase 00 logical v1 contract** under ADR-02/03/04/06/07; executable JSON Schema is a P02 deliverable, not present here. The topic list and MQTT 3.1.1 choice come from draft §4. In MQTT 3.1.1, persistent sessions can queue QoS 1 messages while a client is offline, and QoS 1 messages may be redelivered. ESP-MQTT also retransmits unacknowledged QoS 1 publications; see [OASIS](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/mqtt-v3.1.1.html) and [Espressif](https://docs.espressif.com/projects/esp-idf/en/v5.5.2/esp32/api-reference/protocols/mqtt.html). Analytics consumes persisted backend rows and has no MQTT topic or publish credential.

## Topic and identity rules

Physical base: `irrigation/v1/devices/{deviceId}`. Simulator base: `irrigation/v1/simulations/{runId}/devices/{deviceId}`. Simulator device IDs are globally distinct from physical IDs (for example `sim-plant-01`, never `plant-01`), and the simulation run ID is always recorded separately. A simulator credential has no write permission under the physical base. `deviceId` and `runId` use a bounded ASCII slug, no `/`, `+`, `#`, whitespace or empty segment. The device's configured identity must match topic and payload. The backend subscribes to physical and simulation topics separately, preserving provenance. Only the authenticated backend publishes desired settings or commands; browser never connects directly to MQTT. Broker credentials and ACL must separate device, backend and simulator identities. [Mosquitto configuration](https://www.mosquitto.org/man/mosquitto-conf-5.html) supports password and ACL configuration.

| Suffix | Writer | QoS | Retain | Consumer behavior |
|---|---|---:|---|---|
| `telemetry` | device | 0 | no | Best effort; gaps visible through per-boot sequence. |
| `status` | device/LWT | 1 | yes | `online` only after connection; LWT `offline`; heartbeat age can override retained online state. |
| `events` | device | 1 | no | Deduplicate by `(deviceId, bootId, seq, topic)`; correlate pulse by `pulseId`. |
| `commands` | backend | 1 | no | **Clean session** for device command subscription; no queued offline actuation. Device rejects wrong boot, stale, duplicate or unsafe request. |
| `acks` | device | 1 | no | Upsert progression by command ID; duplicate ACK is harmless. |
| `settings/desired` | backend | 1 | yes | Non-actuating, monotonic revision; validated on device. |
| `settings/reported` | device | 1 | yes | Effective values and rejected revision/reason, if any. |

For a device that subscribes to commands and settings on the same MQTT connection, clean session means it resubscribes on reconnect; the retained desired settings are then delivered again. The API must not report `online` from a retained message alone. An orderly disconnect may not cause LWT, so the backend also uses heartbeat freshness. Broker restart and lost retained state require device republish. Broker delivery and application acceptance are separate outcomes.

## Field schemas to formalize in Phase 02

All JSON messages: UTF-8 object with top-level `schemaVersion=1` and `deviceId` matching the topic and authenticated identity, maximum 2048 encoded bytes and maximum four object/array nesting levels; reject unknown top-level or payload fields in v1, NaN/Infinity, invalid UTF-8, wrong types or unknown schema version. Device-originated telemetry/events/ACKs contain `deviceId`, `bootId`, `seq` (integer 1–4,294,967,295, strictly increasing across sequenced publications in one boot), `uptimeMs` (integer 0–9,007,199,254,740,991, monotonic), `sentAt` (UTC ISO 8601 or null), `timeTrusted` boolean, `source` fixed by authenticated identity, and `payload`. `sentAt` is null when time is untrusted. `seq` covers every sequenced device publication, so a `(deviceId,bootId,seq)` value cannot refer to two different events; the stored topic remains part of the audit record. `bootId` is a fresh UUID per boot; collision or sequence exhaustion forces safe restart/FAULT. Server `receivedAt` is never supplied by the device. Percentages are finite 0–100; distances are finite nonnegative centimeters; durations/intervals are positive integer milliseconds unless suffixed `_s`; RSSI is nullable integer dBm.

| Message | Required payload fields | Invalid/optional rules |
|---|---|---|
| Telemetry | `soilRaw` integer 0–4095 or null, `soilPercent` number or null, `soilQuality` enum `calibrated/uncalibrated/invalid/stale`, `soilAcquiredUptimeMs` integer or null, `tankDistanceCm` number or null, `tankPercent` number or null, `tankQuality` enum `valid/uncalibrated/unknown/stale`, `tankAcquiredUptimeMs` integer or null, `pumpOn` boolean, `mode` enum `AUTO/MANUAL/OFF`, `state` enum `IDLE/WATERING/SOAKING/LOCKOUT/FAULT`, `settingsRevision`, `soilCalibrationRevision`, `tankCalibrationRevision` integers | Percent 0–100 only when quality supports it; invalid raw/distance does not become zero; `wifiRssiDbm` nullable. Acquisition uptime must be `<= uptimeMs`; age is `uptimeMs - acquiredUptimeMs`, stale at `>=15000` ms. Raw ADC range assumes configured 12-bit capture, to be pinned at P04. |
| Status | `availability` enum `online/offline`, `firmwareVersion` nullable, `reason` enum, `bootId` nullable, `publishedAt` nullable | Separate schema, not sequence envelope. A preconfigured LWT can include this boot ID but does not claim a live `seq`, `uptimeMs` or current timestamp. Retained online becomes stale by receipt-age policy. |
| Event | `eventId`, `eventType`, `pulseId` nullable, `commandId` nullable, `triggerSource` enum `AUTO/BUTTON/WEB`, `stateFrom`, `stateTo`, `actualMs` nullable, `reasonCode` nullable | `PULSE_STARTED`, `PULSE_ENDED`, `STATE_CHANGED`, `FAULT_RAISED`, `FAULT_CLEARED` are distinct. A started event is not evidence of completion. |
| Command | `commandId` UUID, `deviceId`, `targetBootId` UUID, `createdAt`, `expiresAt`, `type`, `payload` | `WATER_PULSE` duration integer `1..3000` ms; `expiresAt=createdAt+10000 ms`. No wildcard target, no retain, no auto-reissue under new ID. Device requires trusted UTC; accept only `createdAt <= now < expiresAt`. |
| ACK | `commandId`, `status` enum `accepted/rejected/completed/failed`, `reasonCode` nullable, `pulseId` nullable | Device sequence envelope applies. `accepted` means reservation and safety check passed; `completed` needs observed de-energization and actual runtime. Terminal statuses are immutable. |
| Desired settings | `revision` positive integer, `values` complete settings object, `issuedAt` UTC | Device rejects invalid or older revision and reports effective settings plus rejected revision/reason. No command or physical commissioning fields in settings. |
| Reported settings | `revision`, `values`, `calibrationRevision`, `rejectedRevision` nullable, `reasonCode` nullable | Values represent applied local configuration, not merely requested values. |

Numeric units are milliseconds, seconds, centimeters and percentages as named. `null` denotes unavailable; zero is a real measurement. Schema tests must include missing, extra, wrong-type, out-of-range, version mismatch and identity-mismatch cases. The payload cap is checked before parsing on ESP32. Event and reason registries below are versioned with executable schemas; free-form text never drives control logic. `source` is `device` only under physical topics and `simulator` only under the run namespace. An accepted `timeTrusted=true` message must have nonnull `sentAt`; the reverse also holds. `soilPercent` is nonnull only with `soilQuality=calibrated`; `tankPercent` is nonnull only with `tankQuality=valid`. `pumpOn` is the commanded gate state, not proof of pump current or flow.

The complete v1 settings `values` object contains `mode` (`AUTO/MANUAL/OFF`), `dryThresholdPercent=30`, `wetThresholdPercent=45`, `manualWetCutoffPercent=45`, `sampleIntervalMs=5000`, `maxSampleAgeMs=15000`, `defaultPulseMs=2000`, `maxPulseMs=3000`, `soakMs=60000`, `maxPulsesPerCycle=3`, `maxRolling24hRuntimeMs=20000`, `tankMinPercent` (0–100, exact physically safe value OPEN_HARDWARE), and `consecutiveDrySamples=3`. This initial revision is fixed for deterministic simulation; later editable ranges must stay within firmware hard caps and require their own revisioned schema. `statusStaleMs=30000` is a backend setting, not a device safety setting. A desired message cannot set calibration endpoints or the physical commissioning flag. Reported settings include the same values plus applied `revision` and calibration revision. Device-side hard bounds, not this JSON alone, prevent unsafe changes.

## Command transaction

1. Authenticated API validates mode, requested duration and device freshness. It inserts a `queued` command with a unique `commandId`; it must not claim physical execution.
2. Backend publishes only while the device is fresh/online and only before `expiresAt`. Publish success means broker acceptance, not device acceptance. No automatic retries under a new command ID.
3. Device requires matching `targetBootId`, trusted UTC time for `createdAt`/`expiresAt`, valid payload, safety guards and no prior reservation for `commandId`. If clock is untrusted, reject `CLOCK_UNTRUSTED` (button and local auto remain possible). Remote actuation after a cold offline boot is therefore unavailable until time sync, as accepted in ADR-03. Device checks the MQTT retained flag and rejects retained actuation even if JSON otherwise passes.
4. Before pump energization, device records a durable reservation for the ID. If this write fails, reject. Then emit `accepted`; a power failure between reservation and actuation may yield **zero** watering, which is safe. If a duplicate arrives, replay the known terminal ACK or respond with `DUPLICATE_IN_PROGRESS`; never reserve/start again.
5. Once started, one `pulseId` binds start/end events and the command. On normal cutoff send `completed` with actual runtime. On any interruption send `failed` if possible; after reboot a previously reserved nonterminal command is reconciled as `failed/INTERRUPTED` and is never resumed. Late/duplicate ACKs do not regress terminal status.
6. If ACK is lost, backend marks outcome `unknown` after timeout and reconciles with event/telemetry; it must not silently label it completed or republish actuation. API/UI shows `queued`, `published`, `accepted`, `completed`, `rejected`, `failed` or `unknown`, with timestamps and reason.

Device cache capacity and flash wear budget are P04 design parameters; no unsafe eviction is permitted. Retain at least all IDs accepted for the current boot until their UTC expiry plus a 30 s reconciliation margin, and never evict an active/nonterminal ID. UTC expiry plus boot binding protects old commands after eviction. On reboot, the old `targetBootId` is rejected. Test crash points before reservation, after reservation, after energizing and after de-energizing. A retained actuation command, persistent command session or any command without target boot must fail contract tests. If the durable ledger cannot guarantee these invariants, device enters FAULT and leaves gate OFF.

## Reconnect and settings reconciliation

On connect, device publishes online status and current reported settings; backend resubscribes and reconstructs last-seen from fresh messages. Retained desired settings are validated and applied only if revision is greater than local applied revision. A duplicate revision is a no-op and is reported again. A rejected revision never replaces the effective local settings. Backend stores desired and reported separately; UI displays `pending`, `applied` or `rejected`. Settings that affect safety must be written atomically on device with checksum/version, within firmware hard bounds; unsafe or malformed values are rejected. Remote calibration procedure must require physical validation before becoming effective; a desired message alone cannot make uncalibrated sensors safe.

## Status, ACK and reason registries

Status v1 outer object is `{schemaVersion,deviceId,source,payload}` with payload `{availability,reason,firmwareVersion,bootId,publishedAt}`. A retained online publication uses `reason=CONNECTED`, a nonnull boot ID and the device's trusted UTC or null. The preconfigured retained LWT uses `availability=offline`, `reason=LWT`, the current boot ID and `publishedAt=null`; it has no `seq` or `uptimeMs`. Backend marks status `stale` when **30,000 ms or more** have elapsed since its last fresh validated device publication, even if retained status says online. On reconnect, device republishes status/reported settings. Broker presence is not physical proof of pump state.

Canonical command transitions: `queued→published→accepted→completed|failed`; `queued|published→rejected`; `queued|published|accepted→unknown` only as a backend timeout observation. A later valid device terminal ACK may reconcile `unknown→completed|failed|rejected` if correlated, but no terminal state regresses. Duplicate ACK with identical content is a no-op; conflicting terminal ACK raises integrity alert. `accepted` means durable reservation, **not water delivery**. `completed` means device observed gate OFF and recorded duration, **not measured water flow**. Events and ACKs may arrive out of order; store raw observations and derive canonical status transactionally.

Reason-code registry v1: status `CONNECTED`, `LWT`, `ORDERLY_DISCONNECT`; command/safety/settings `CLOCK_UNTRUSTED`, `COMMAND_EXPIRED`, `COMMAND_NOT_YET_VALID`, `BOOT_MISMATCH`, `RETAINED_COMMAND`, `DUPLICATE_IN_PROGRESS`, `INVALID_SCHEMA`, `UNAUTHORIZED_IDENTITY`, `SOIL_UNCALIBRATED`, `SOIL_STALE`, `SOIL_WET`, `TANK_UNKNOWN`, `TANK_LOW`, `BUDGET_EXHAUSTED`, `COMMISSIONING_REQUIRED`, `BUSY_OR_LOCKED`, `LEDGER_WRITE_FAILED`, `INTERRUPTED`, `HARD_TIMEOUT`, `SENSOR_TRIP`, `SETTINGS_INVALID`, `SETTINGS_REVISION_OLD`. Event types v1: `PULSE_STARTED`, `PULSE_ENDED`, `STATE_CHANGED`, `FAULT_RAISED`, `FAULT_CLEARED`. Unknown reason/event codes are stored as invalid diagnostics and cannot drive control/UI conclusions. HTTP/API validation errors map to structured code and message; secrets and raw payloads are not reflected to users.

## Illustrative valid and invalid packets

Valid physical telemetry (`sentAt=null` means it is unsuitable for time-based analytics):

```json
{"schemaVersion":1,"deviceId":"plant-01","bootId":"00000000-0000-4000-8000-000000000001","seq":12,"uptimeMs":120000,"sentAt":null,"timeTrusted":false,"source":"device","payload":{"soilRaw":2140,"soilPercent":42,"soilQuality":"calibrated","soilAcquiredUptimeMs":119500,"tankDistanceCm":13.2,"tankPercent":64,"tankQuality":"valid","tankAcquiredUptimeMs":119400,"pumpOn":false,"mode":"AUTO","state":"IDLE","settingsRevision":1,"soilCalibrationRevision":1,"tankCalibrationRevision":1,"wifiRssiDbm":-59}}
```

Valid command structure (the literal timestamps are an example, **not** currently valid for actuation):

```json
{"schemaVersion":1,"commandId":"00000000-0000-4000-8000-000000000002","deviceId":"plant-01","targetBootId":"00000000-0000-4000-8000-000000000001","createdAt":"2026-11-06T15:00:00.000Z","expiresAt":"2026-11-06T15:00:10.000Z","type":"WATER_PULSE","payload":{"durationMs":2000}}
```

Invalid example: the same command with `durationMs=4000` fails `INVALID_SCHEMA`; a command with matching JSON published with MQTT retain=true fails `RETAINED_COMMAND`; `source="simulator"` on a physical topic fails `UNAUTHORIZED_IDENTITY`; an ACK `completed` without a reserved command is quarantined for reconciliation and cannot create a completed command by itself. These are intended contract assertions, not executed test outcomes.
